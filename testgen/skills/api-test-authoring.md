# API-тест

Если сценарий помечен как тест API (бэкенд), проверяй правило запросами `api_request`, а не через интерфейс.

## Запросы
- Пути — относительно адреса приложения: `/api/clubs`, `/api/tournaments/{{vars.tournament_id}}`.
- Запросы идут с куками браузера: если API требует входа, сначала войди через интерфейс
  (или тест начинается с сохранённым входом проекта).
- Тело — JSON. Данные, которые должны быть новыми на каждом прогоне, — плейсхолдерами:
  `{"name": "Товар {{unique}}", "email": "{{faker.email}}"}`.
- `DELETE` запрещён. Не вызывай оплату, отправку писем и другие необратимые действия.

## Проверки
- Каждый запрос проверяет ожидаемый статус (`expect_status`): 200/201 для успеха, 400/422 для неверных
  данных, 401/403 для запрета, 404 для несуществующего.
- Проверяй поля ответа (`expect_json`): `{"$.status": "open", "$.club.id": "{{vars.club_id}}"}`. Не только
  статус: тест, проверяющий лишь 200, пройдёт при неверных данных.
- Ответ показывается тебе после шага — по нему выбирай поля для следующих проверок.
- Идентификатор созданного объекта сохраняй (`save`: `{"tournament_id": "$.id"}`) и используй дальше
  как `{{vars.tournament_id}}`: например, прочитай созданный объект GET-запросом и проверь его поля.

## Негативные и проверки прав
- Неверные данные: обязательное поле пустое, неверный формат, значение за границей — ожидай 400/422 и
  поле ошибки в ответе.
- Права: запрос от роли без доступа — ожидай 403, к чужому объекту — 403 или 404.
