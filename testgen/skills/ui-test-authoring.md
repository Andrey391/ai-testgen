# Запись UI-теста

## Шаги
- Один шаг — одно действие пользователя. Описание в повелительном наклонении, с названием элемента
  в кавычках: «Нажать кнопку 'Войти'», «Ввести 'kindle' в поле поиска».
- Выбирай элементы с понятным текстом или подписью: такие локаторы устойчивее при повторных прогонах.
- Не добавляй лишних кликов «на всякий случай» и не исследуй сайт: тест должен быть кратчайшим путём.

## Проверки
- После каждого значимого изменения состояния добавляй проверку: появился результат поиска, товар
  в корзине, сообщение об ошибке, сменился URL.
- Каждый сценарий заканчивается проверкой **результата**, а не только видимости: не «кнопка
  "Оформить" видна», а «в корзине 1 товар, сумма 29.99», «поле Email содержит введённый адрес»,
  «сообщение "Заказ сохранён" в блоке уведомлений». `assert_visible` доказывает лишь, что элемент есть
  на странице: тест с такой последней проверкой пройдёт, даже если действие не сработало.
- Выбирай проверку по смыслу результата:
  - текст сообщения или данные в конкретном блоке — `assert_element_text` (или `assert_text_present`);
  - значение поля формы после ввода или загрузки — `assert_value`;
  - число строк, карточек, товаров в корзине — `assert_count`;
  - флажок, переключатель — `assert_checked`; кнопка стала доступной или заблокированной — `assert_enabled`;
  - переход на другую страницу — `assert_url_contains`.
- Тест проверяется мутациями: его прогоняют на странице, где действие не срабатывает, результат
  скрыт или изменён, а API отвечает ошибкой. Хорошие проверки падают на каждом таком мутанте.
- `assert_no_console_errors`, `assert_accessible` и `assert_screenshot` — дополнительные проверки, а не
  проверка результата; добавляй их, когда сценарий о них просит.
- Проверяй стабильный текст (заголовки, сообщения), а не динамический (время, случайные номера, цены
  со скидкой, если сценарий не про них).
- Для негативных сценариев проверяй конкретный текст ошибки, а не просто то, что что-то не произошло.
- Тест обязательно заканчивается проверкой ожидаемого результата сценария.

## Ожидания
- Не ставь ожидание «на всякий случай»: следующая проверка сама дождётся элемента.
- Явное ожидание нужно только для анимаций и отложенной загрузки, которые ломают следующий шаг.

## Данные
- Используй тестовые данные из сценария. Если их нет — придумай правдоподобные и безопасные
  (example.com для почты, тестовые номера).
- Данные, которые должны быть новыми при каждом прогоне (e-mail и логин при регистрации, название
  создаваемого объекта), вводи плейсхолдерами: `{{faker.email}}`, `{{faker.name}}`, `{{faker.phone}}`,
  `{{unique}}` (например «Заказ {{unique}}»), `{{today}}`. Литерал сломает второй прогон
  («пользователь уже существует»). Внутри одного прогона плейсхолдер даёт одно и то же значение —
  его можно ввести при регистрации и потом при входе и проверить.
