# Виды проверок

Тип сценария (`type`) — это то, *что* он доказывает. Проектируй сценарии только тех типов, что выбраны
для генерации, но внутри каждого типа покрывай требования полностью.

## Функциональные
- **positive** — основной поток с корректными данными доходит до ожидаемого результата. По одному на каждую
  пользовательскую историю и каждый альтернативный путь, который меняет результат.
- **negative** — неверный ввод или запрещённое действие отклоняется: понятное сообщение, данные не меняются,
  пользователь может исправить ошибку.
- **validation** — обязательные поля, форматы (email, телефон, дата), длины, допустимые значения, пробелы
  по краям, регистр. Объединяй однотипные поля одной формы в один сценарий с таблицей данных.
- **boundary** — значения на границах: минимум, максимум, на единицу за ними, пусто, ноль.
- **edge** — необычные, но допустимые ситуации: пустой список, один элемент, очень длинный текст,
  спецсимволы и эмодзи, повторное действие, возврат назад.
- **state_transition** — жизненный цикл объекта: каждый разрешённый переход и важные запрещённые
  (нельзя отменить отправленный заказ, нельзя оплатить отменённый заказ).
- **error_handling** — как система сообщает о сбоях: ошибка сервера, нет связи, данные удалены другим
  пользователем. Проверяй сообщение и то, что данные не испорчены.
- **data_integrity** — созданное и изменённое сохраняется, одинаково показано во всех местах (список,
  карточка, отчёт), не дублируется при повторной отправке.
- **integration** — результат одного модуля — вход другого: товар, созданный менеджером в админке, виден
  в каталоге и попадает в корзину.

## Доступ и безопасность
- **roles** — для каждой роли: что она видит и может, и что ей запрещено. Запрет проверяй и через интерфейс
  (кнопки нет), и через прямой переход по адресу.
- **security** — вход и выход, сессия после выхода, доступ к чужим данным подменой id в адресе (IDOR),
  ввод `<script>alert(1)</script>` и `' OR 1=1 --` в поля (значение должно показаться как текст, без
  выполнения и без ошибки сервера), блокировка после неудачных попыток входа, отсутствие пароля в ответах.
  Только безопасные проверки на тестовом стенде, без нагрузки и без реальных атак.

## Нефункциональные
- **accessibility** — работа с клавиатуры, подписи полей и кнопок, фокус, контраст; `assert_accessible`
  проверяет правила WCAG.
- **usability** — пользователь понимает, что произошло: сообщения, подсказки, подтверждения опасных действий.
- **compatibility** — тот же поток в другом браузере и на мобильном экране.
- **localization** — тексты, даты, числа и валюты нужной локали, длинные переводы не ломают вёрстку.
- **performance** — действие завершается за ожидаемое время, списки с большим числом элементов работают
  (пагинация, поиск). Без нагрузочного тестирования.

## Правила
- У каждого сценария явные предусловия: какие данные, роли и состояния объектов нужны (из модели
  приложения проекта, если она есть).
- Ожидаемый результат проверяем: конкретный текст, значение, число, адрес или статус ответа API.
- Не дублируй: если два сценария отличаются только данными — это один сценарий с несколькими наборами данных.
