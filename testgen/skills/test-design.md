# Тест-дизайн сценариев

## Покрытие
- Начинай с основного позитивного пути каждой пользовательской истории, затем добавляй альтернативные пути.
- Для каждого поля ввода примени классы эквивалентности (валидные / невалидные значения) и граничные значения
  (минимум, минимум−1, максимум, максимум+1, пусто) — но выноси в отдельный сценарий только те проверки,
  что реально различаются поведением системы.
- Негативные сценарии: обязательные поля, неверный формат, недостаточные права, повторная отправка,
  состояние «нет данных».
- Если в требованиях есть статусы или жизненный цикл объекта — проверь ключевые переходы состояний.
- Не дублируй сценарии, отличающиеся только тестовыми данными: объедини их и перечисли данные в инструкциях.

## Приоритеты
- high — основной бизнес-поток и всё, что блокирует пользователя или влияет на деньги и данные.
- medium — альтернативные пути и валидации.
- low — косметика, редкие граничные случаи.

## Формат инструкций для агента
- Пиши шаги, которые выполнимы в браузере с этой страницы: что открыть, что ввести (с конкретными данными),
  что нажать.
- Последний шаг — что именно проверить на экране (текст, элемент, URL).
- Не требуй проверок, которые нельзя сделать через интерфейс или API приложения (БД, логи, письма).
- Сценарий слоя API описывает запросы (метод, путь, тело) и ожидаемый статус и поля ответа.
- Если сценарий требует необратимого действия (оплата, отправка, удаление) — доведи до этой точки
  и проверь, что она достигнута.
