## 1. Назначение системы

Веб-студия генерации автотестов с ИИ. Человек описывает проверку обычным языком (или даёт ТЗ, ручной кейс,
адрес сайта), ИИ-агент проходит её в настоящем браузере и записывает исполняемый тест: шаги, устойчивые
локаторы, проверки. Тесты прогоняются в регрессии и CI, выгружаются в pytest-playwright / Gherkin.

Ключевой принцип: **ИИ предлагает — человек решает.** Черновик теста, новый локатор самолечения, замечания
ревьюера, изменения модели приложения — всё ждёт решения человека в счётчике «Ждёт вас».

## 2. Структура интерфейса (что видно на `/`)

**Шапка:** выбор проекта (select «Проект»: kimi / TT / Проверка слияния / ТТ 2), «+» (новый проект),
«Все проекты», меню вкладок, «История проверок» (своя у вкладки), «Справка» (→ `/guide`), счётчик
«Ждёт вас» (на карте — «0»).

**Меню в порядке работы:** Требования · Конвейер · Studio · Тесты | Задачи · Дашборд | Проект.

**Открытая вкладка на момент обхода — «Требования»:**
- свёрнутый блок «＋ Проверить новые требования — ТЗ из Jira, Confluence, трекера, файла или текстом»:
  поле ссылки (placeholder `https://company.atlassian.net/browse/PROJ-123 · …/wiki/spaces/TEAM/pages/12345`),
  textarea текста (placeholder «Как покупатель, я хочу добавлять товары в корзину…»), «Проверить требования»;
- карточка текущего анализа: заголовок, «🔗», статус «не проверены», «Удалить», дата/источник;
- шаги-вкладки анализа: «1. Требования не проверены → 2. Замечания — → 3. Жизненный цикл — →
  4. Сценарии и тесты после шагов 1–3»;
- «Вставить в поле новых требований».

## 3. Функциональные области

### 3.1 Проекты и мастер нового проекта
- Мастер: 1) Приложение (название, URL стенда) → 2) Модель ИИ (модель, ключ/адрес, «Проверить») →
  3) Подключения (Jira/Confluence, Test IT, Allure TestOps, Zephyr; проверка каждого) → 4) Процесс
  (подключения ↔ этапы) → 5) «С чего начать»: познакомиться с системой / проверить требования /
  автоматизировать ручные кейсы / записать тест в Studio.
- Без проектов студия сама открывает мастер. Проект открывается на вкладке, где его оставили.
- Переключение проекта в шапке; «Все проекты».

### 3.2 Требования (ревью ТЗ)
- Ввод: ссылка Jira/Confluence, файл или текст → «Проверить требования».
- Ревьюер (ИИ на чистом контексте) проверяет по стандарту (ГОСТ 34.602, ГОСТ 19.201, ISO/IEC/IEEE 29148,
  user story) и сверяет с моделью приложения; живая лента хода.
- Шаги анализа, у каждого одна главная кнопка:
  1. **Требования** — текст, «История изменений ТЗ», «Источник» / «Сверить с источником», «Новая версия ТЗ».
  2. **Замечания** — ответ «как должно быть» / «Принять предложение» / «Не актуально» с причиной;
     массово: «Скопировать для аналитика», «Вставить ответы аналитика», «Принять предложения ревьюера»;
     «Исправить ТЗ агентом». Ответ без исправления ТЗ = «ждёт исправления в ТЗ» (не разобрано).
  3. **Жизненный цикл** — расхождения с моделью; обновления модели («Принять все» / «Отклонить все» /
     «Разобрать по одному»); подтверждение затронутых частей модели.
  4. **Сценарии и тесты** — «Генерировать тест-кейсы в конвейере →» (активна только когда всё разобрано);
     «Путь к тест-дизайну» — чек-лист из 7 пунктов.
- «История проверок» — окно со всеми анализами проекта; «Удалить» анализ.
- Одна работа над анализом за раз: параллельное действие → 409 «Сейчас идёт: …»; «Остановить».

### 3.3 Конвейер
- Источник (один на запуск): «Проверенные требования» / «Сценарии из анализа» / «Ручные кейсы» /
  «Обход сайта» (Planner).
- Этапы: ревью → сценарии (слои UI/API, виды проверок, техники) → отбор (вручную / все / только high) →
  генерация агентом (видна в Studio) → прогон → мутации → публикация.
- Пункт ждёт только своих решений (замечания кейса, части модели, похожий сценарий: reuse / refine / new).
- «Продолжить», «Перезапустить сбойные (N)», «Остановить», «Отменить запуск», «Отменить» у пункта,
  «Запустить всё равно» (только при стопе по жизненному циклу); «История запусков», «Новый запуск».

### 3.4 Studio
- Форма «Новый тест»: название, сценарий; подсказка, что агент учтёт из модели.
- «Начать генерацию» → Live View; шаг: «Выполнить шаг» (Enter) / «Отклонить» (Esc) с подсказкой;
  Auto-Pilot; «Остановить агента» (Ctrl+.), «Продолжить с агентом»; чат.
- Режимы клика по Live View: Смотреть / Записывать (Record & Play) / Выбрать элемент (Element Picker).
- Правка шагов: описание, ▲▼, ✕, «+ шаг»; «Сохранить» (тест → «Тесты» как черновик).
- «Открытые сессии» (по одной на проект, лимит на человека), «Прерванные сессии» → «Продолжить» /
  «Все прерванные». Происхождение сессии и «Вернуться к …».
- API-тест: вместо Live View — запросы и ответы.

### 3.5 Тесты
- Список: поиск, фильтры (статус: черновик / на ревью / в наборе; здоровье: падающие, нестабильные,
  карантин, слабые, самолечение, устаревшие; слой; тег; задача). Одна кнопка «Запустить» + «Ещё ▾».
- «Ещё ▾»: Прогон в Studio, Проверить мутациями, теги, статус, карантин, «Сделать тестом входа» /
  «Сделать обычным тестом», «Сделать модулем», экспорт .py / .feature / API (httpx).
- Карточка: история изменений (сравнить, откатить), последние прогоны / «Все прогоны», ревью самолечения
  (Принять / Отклонить), «Тест актуален», «Править в Studio», «Связано», запросы сценария.
- Прогон: упавшие шаги, анализ причины (дефект продукта / проблема теста / окружение / нестабильность),
  «Черновик дефекта», «Править шаг» → «Сохранить и повторить», «Разобрать с агентом», «Открыть в Studio»,
  «Повторить».
- Наборы: «Запустить набор» (все / по тегу), «Параметры прогона» (экран, видимое окно, с черновиками),
  «Повторить упавшие», «Запуски наборов»; тесты с общими данными — по очереди.
- «Покрытие экранов» (страницы без тестов), «Импорт кейсов», «Экспорт ▾ → Проект pytest (.zip)».

### 3.6 Задачи
- Список задач: статус (todo / в работе / на проверке / готово), приоритет, исполнитель, срок, тесты.
- «Тест в Studio» из задачи — тест привязывается при сохранении; подсказка статуса по тестам (меняет человек).

### 3.7 Дашборд
- Состояние тестов, время регрессии, расход ИИ, сэкономленные часы, автоматизированные ручные кейсы,
  «Решений людей на тест», «Ожидание решений по видам». Плитки ведут на отфильтрованный список тестов.

### 3.8 Проект (настройки)
- Проект: Общие (URL приложения, уведомления — Telegram/Mattermost/почта), Участники и доступ (наблюдатель /
  редактор / владелец, «Открыть журнал»).
- Подключения: Модель (модель, effort, ключ, цены), Подключения (MCP), API приложения (адрес, авторизация,
  эндпоинты), Доступ из IDE (MCP).
- Тест-дизайн: Требования (стандарт, Planner: лимиты, тест входа), Сценарии (умолчания), Тестовые данные
  (Обзор и подтверждение с диаграммами Простая / Зависимости / Подробная, «Исследовать сайт», «Подтвердить»;
  Обновления, Дубли, Сущности, Роли, Учётные записи, Данные, Память), Скиллы (вкл/выкл, «Клонировать в проект»).
- Генерация и прогоны: Процесс генерации (этапы, «Решения команды», «Лимиты расхода», «Сохранить процесс»),
  Повторяющиеся шаги («Сделать модулем»).

### 3.9 Сквозные элементы
- «Ждёт вас»: число решений (до «99+»), список, «Мои решения» со сроками; опрос раз в 30 с.
- У каждого экрана свой адрес (`#/p/{pid}/{req|pipe|studio|tests|…}`); чужое → «Не найдено или нет доступа».
- Окна истории закрываются ✕, Esc, кликом рядом.
- `/guide` — руководство + словарь, «← В студию».

## 4. Бизнес-правила, которые должны проверять тесты

1. Тест-дизайн по требованиям недоступен, пока не разобраны блокирующие замечания (ответ внесён в ТЗ или
   «Не актуально»), модель не обучена и затронутые части не подтверждены — кнопка неактивна, API 409.
2. Ответ на замечание без «Исправить ТЗ агентом» не разблокирует тест-дизайн.
3. Одна работа над анализом за раз — второе действие получает «Сейчас идёт: …».
4. Тест агента — черновик; в набор только после ревью (или «По риску» при мутациях ≥ порога).
5. Самолечение в режиме review не меняет тест без «Принять».
6. Модуль, который вызывают тесты, удалить нельзя — показывается список тестов.
7. Подтверждённая модель не меняется молча: изменения → «Обновления».
8. Изменение ТЗ / сценария / модели помечает связанные тесты «Устарел»; «Тест актуален» снимает отметку.
9. Пароль нигде не виден: в шагах `{{password}}`, в интерфейсе — «задан».
10. Роли проекта: наблюдатель только смотрит; редактор — тесты и запуски; владелец — настройки.
11. Лимит открытых сессий Studio на человека → вопрос, какую закрыть.
12. Planner не отправляет формы и пропускает выход / удаление / скачивание.

## 6. Рекомендации

**По Planner (чтобы такой обход давал сценарии сам):**
1. Учитывать SPA: нажимать безопасные кнопки навигации (`data-tab`, `role=tab`, пункты `nav`) и сохранять
   hash-маршруты как отдельные страницы (не отрезать `#/…` в `_norm`, если фрагмент — маршрут).
2. Брать больше текста для текстовых страниц (справка, «О продукте») — хотя бы оглавление `h2/h3` целиком
   и первые абзацы разделов; поднять лимит кнопок и учитывать кнопки внутри форм.
3. Не собирать пользовательские данные как функциональность (списки проектов, история).
4. Пустой план считать сбоем с причиной («карта: 2 страницы, 1 форма — мало для сценариев; задайте тест
   входа / увеличьте лимиты / приложите ТЗ»), а не `warn`.
5. Смягчить «не придумывай функции» до «выводи из видимых элементов; базовые проверки навигации и
   валидации форм делай всегда» — чтобы даже тонкая карта давала сценарии раздела 5.

**По этой студии:** для полноценного тест-дизайна дать конвейеру справку `/guide` как требования
(источник «текст»/ссылка) — в ней описаны все сценарии работы, роли и правила раздела 4.
