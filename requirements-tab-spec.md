# Требования к разделу «Требования» (ревью ТЗ) — для тестирования

Версия 1.0 · 26.10.2026 · Система: AI Test Generator (веб-студия), стенд http://localhost:8765/

Документ описывает поведение вкладки «Требования» так, чтобы по нему можно было проектировать тест-кейсы:
у каждого требования есть идентификатор (`ТР-…`), однозначная формулировка и проверяемый критерий приёмки.
Источник — справка `/guide`, CLAUDE.md и код студии (`server.py`, `testgen/review.py`, `testgen/analyses.py`,
`testgen/sources.py`, `static/index.html`). Документ можно подать в студию как требования (вкладка
«Требования» → текст или файл .md).

---

## 1. Назначение и границы

**Назначение раздела.** Проверить документ требований (ТЗ, user story) ревьюером — ИИ-субагентом с чистым
контекстом, — дать людям разобрать замечания и довести требования до состояния «готовы к тест-дизайну».

**Входит в раздел:** ввод требований, проверка ревьюером, разбор замечаний, исправление ТЗ агентом, версии ТЗ,
сверка с жизненным циклом модели приложения, подтверждение модели, история проверок, переход в конвейер.

**Не входит:** генерация сценариев и тестов (только во вкладке «Конвейер»), настройки стандарта и Planner
(«Проект → Тест-дизайн → Требования»), редактирование модели приложения («Проект → Тестовые данные»).

## 2. Термины

| Термин | Значение |
|---|---|
| Анализ | Запись о проверке одного документа требований: текст, версии, отчёт ревьюера, решения, сценарии |
| Ревьюер | ИИ-субагент, проверяющий документ по стандарту и модели приложения |
| Замечание | Дефект документа (`d<i>`), расхождение с жизненным циклом (`l<i>`) или вопрос автору (`vq<i>`, `lq<i>`) |
| Тема | Группа замечаний об одном и том же; номер темы — 1, 2… (документ) и Ж1, Ж2… (жизненный цикл) |
| Блокирующее замечание | Замечание, без разбора которого тест-дизайн по анализу недоступен |
| Модель приложения | Сущности, статусы, переходы, роли и ограничения системы («Тестовые данные») |
| Работа над анализом | Длительная операция: проверка, исправление ТЗ, разбор ответов, темы, сверка ЖЦ, обучение модели, проектирование |

## 3. Роли и доступ

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-01 | Наблюдатель проекта видит анализы и отчёты, но не может запускать проверку, принимать решения по замечаниям, исправлять ТЗ и удалять анализ | Запросы наблюдателя к `POST /api/requirements/review`, `PUT …/review/findings`, `POST …/review/fix`, `DELETE /api/analyses/{aid}` возвращают 403; кнопки действий в интерфейсе недоступны |
| ТР-02 | Редактор и владелец выполняют все действия раздела | Каждое действие раздела у редактора завершается успешно |
| ТР-03 | Анализ чужого проекта недоступен | `GET /api/analyses/{aid}` для анализа проекта без доступа → 404 «Анализ не найден» / «Не найдено или нет доступа» в интерфейсе |
| ТР-04 | Без настроенной модели ИИ проверка, разбор ответов и исправление ТЗ не запускаются | Ответ — ошибка с указанием настроить модель в «Проект → Модель»; анализ не создаётся |

## 4. Функциональные требования

### 4.1 Ввод новых требований

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-10 | Блок «＋ Проверить новые требования» свёрнут, если в проекте есть анализы, и раскрывается по клику | Есть хотя бы один анализ → блок свёрнут; клик раскрывает поле ссылки, поле текста, выбор файла и кнопку «Проверить требования» |
| ТР-11 | Требования принимаются одним из способов: ссылка (Jira, Confluence, а также YouTrack, Яндекс Трекер, Kaiten через подключения проекта), файл, текст | Каждый способ по отдельности приводит к созданию анализа |
| ТР-12 | Ссылка Jira распознаётся в формах `…/browse/PROJ-123`, `…?selectedIssue=PROJ-123` и как ключ `PROJ-123` (регистр не важен); Confluence — `…/wiki/…` или числовой ID страницы | Каждая форма загружает соответствующий документ |
| ТР-13 | Нераспознанная ссылка отклоняется с подсказкой | Ссылка `http://example.com/page` → «Не удалось распознать ссылку: нужна ссылка на задачу Jira (…/browse/PROJ-123) или страницу Confluence (…/wiki/spaces/…/pages/…)»; строка `abc` → «Укажите ссылку на Jira/Confluence, ключ задачи (PROJ-123) или ID страницы»; анализ не создаётся |
| ТР-14 | Поддерживаемые файлы: .docx, .pdf, .md, .markdown, .txt; можно выбрать несколько файлов | Другой формат (например, .xlsx) → «Поддерживаются файлы .docx, .pdf, .md и .txt» |
| ТР-15 | Файл больше 30 МБ не принимается | Файл 30 МБ + 1 байт → «Файл больше 30 МБ»; файл ровно 30 МБ принимается |
| ТР-16 | Повреждённый файл и файл без текста отклоняются с понятной причиной | Битый .docx → «Не удалось прочитать файл <имя>: он повреждён или это не DOCX»; PDF-скан без текстового слоя → «В файле <имя> нет текста (скан без распознавания?)» |
| ТР-17 | Текст требований не длиннее 200 000 символов | 200 000 символов — принимается; 200 001 → «Текст требований больше 200 000 символов (200 001)»; текст файла длиннее лимита обрезается до 200 000 с пометкой об обрезке |
| ТР-18 | Пустой ввод не запускает проверку | Пустые поля или текст только из пробелов/переводов строк → «Нет текста требований» |
| ТР-19 | Повторная проверка того же текста обновляет существующий анализ, а не создаёт дубль | Повторный ввод идентичного текста: число анализов не меняется, в ленте — «Эти требования уже проверялись: обновляю их анализ…», прежние решения учитываются |

### 4.2 Проверка ревьюером

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-20 | Проверка выполняется по стандарту проекта: ГОСТ 34.602, ГОСТ 19.201, ISO/IEC/IEEE 29148 или user story | В отчёте указан стандарт; замечания о разделах соответствуют выбранному стандарту |
| ТР-21 | Ревьюер находит дефекты документа (разделы по стандарту, качество требований, правила команды, вопросы авторам) и расхождения с жизненным циклом модели (статусы, переходы, зависимости, роли и их ограничения, пробелы ЖЦ, новое для модели) | Отчёт содержит две группы: «Замечания» (шаг 2) и «Жизненный цикл» (шаг 3) |
| ТР-22 | Ход проверки отображается живой лентой | Во время проверки в карточке появляются строки хода; ответ API — поток NDJSON с событиями `analysis`, `log`, `review`, `done` или `error` |
| ТР-23 | Проверка продолжается на сервере после закрытия или перезагрузки страницы | Запустить проверку, нажать F5 → карточка показывает текущий ход и завершение без повторного запуска |
| ТР-24 | Проверку можно остановить | «Остановить» → статус «Проверка остановлена» (`cancelled`); прежний отчёт (если был) сохраняется; уже завершённые части при повторном запуске не перепроверяются |
| ТР-25 | Сбой модели ИИ показывается текстом ошибки, анализ переходит в статус «ошибка» | Недоступная модель / неверный ключ → сообщение об ошибке в карточке, статус `error` |
| ТР-26 | «Проверить заново» передаёт ревьюеру решения авторов по прежним замечаниям | Отклонённое «Не актуально» замечание при повторной проверке не возникает снова в том же виде |

### 4.3 Карточка анализа и шаги

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-30 | В окне один выбранный анализ (по умолчанию последний); остальные — в окне «История проверок» | Кнопка «История проверок» в шапке открывает список всех анализов проекта; выбор анализа открывает его карточку |
| ТР-31 | Окно истории закрывается ✕, клавишей Esc и кликом вне окна | Каждый способ закрывает окно без изменения выбранного анализа |
| ТР-32 | Карточка содержит шаги-вкладки «1. Требования → 2. Замечания → 3. Жизненный цикл → 4. Сценарии и тесты» | До проверки шаги 2–3 показывают «—», шаг 4 — «после шагов 1–3» |
| ТР-33 | У каждого шага одна главная кнопка; разобранный шаг сворачивается в «✓ … → Дальше» | После разбора всех замечаний шаг 2 показывает «✓ … → Дальше», клик открывает шаг 3 |
| ТР-34 | Шаг 1 показывает текст требований, «История изменений ТЗ», для загруженных по ссылке — «Источник» и «Сверить с источником», кнопку «Новая версия ТЗ» | Все элементы присутствуют; для текстового ввода «Источник» отсутствует |
| ТР-35 | «Удалить» анализ требует подтверждения и удаляет только анализ — тесты, созданные по его сценариям, остаются | Отмена подтверждения ничего не удаляет; после удаления тесты есть во вкладке «Тесты» |
| ТР-36 | «Вставить в поле новых требований» переносит текст анализа в форму новых требований | Текст анализа появляется в поле текста блока ТР-10 |

### 4.4 Разбор замечаний (шаг 2)

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-40 | У замечаний номера тем: 1, 2… для документа, Ж1, Ж2… для жизненного цикла | Номера уникальны в анализе и совпадают в интерфейсе и в тексте «Скопировать для аналитика» |
| ТР-41 | По замечанию можно: ввести ответ «как должно быть», принять предложение ревьюера, отметить «Не актуально» с причиной | Ответ/принятие → статус «ждёт исправления в ТЗ» (`todo`); «Не актуально» → `dismissed`; «Не актуально» без причины не сохраняется |
| ТР-42 | Ответ без исправления ТЗ не считается разбором | Замечание в `todo` не открывает тест-дизайн; в «Пути к тест-дизайну» пункт 3 не отмечен |
| ТР-43 | Решение по несуществующему замечанию отклоняется | `PUT …/review/findings` с неизвестным ID → 404 «Замечание не найдено: проверьте требования заново» |
| ТР-44 | «Скопировать для аналитика» копирует в буфер все неразобранные замечания с номерами тем | Буфер содержит номера и формулировки всех открытых тем шага |
| ТР-45 | «Вставить ответы аналитика» принимает один текст до 200 000 символов и разносит ответы по темам (по номеру, коду или коду замечания) | Ответ «2: поле обязательно» попадает в тему 2 со статусом `todo`; ответ «не актуально» — `dismissed` |
| ТР-46 | Пустой и слишком длинный текст ответов отклоняются | Пусто → «Вставьте ответы аналитика»; 200 001 символ → сообщение о лимите с советом разбить или загрузить «Новая версия ТЗ» |
| ТР-47 | Неразнесённые ответы показываются с причиной, текст сохраняется до полного разнесения | Ответ на несуществующую тему → в списке «не разнесено» с причиной; после F5 текст на месте; «Очистить» удаляет его |
| ТР-48 | «Принять предложения ревьюера» принимает предложения по всем открытым замечаниям шага | Все открытые замечания с предложением переходят в `todo` |
| ТР-49 | «Исправить ТЗ агентом» вносит ответы в текст ТЗ; замечание после внесения — исправлено (`fixed`) | Текст ТЗ содержит правку; в «История изменений ТЗ» — запись с текстом до изменения; без замечаний в `todo` → «Нет замечаний для исправления: ответьте на замечания или примите предложения ревьюера» |
| ТР-50 | Исправление идёт пакетами; «Остановить» или сбой теряют только пакеты в работе | Остановить исправление после первого пакета → правки первого пакета сохранены |

### 4.5 Версии ТЗ

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-55 | «Новая версия ТЗ» (текст или файл) заменяет текст анализа, прежний сохраняется в истории, документ проверяется заново с учётом решений | В истории — запись вида «версия»; в ленте — «Новая версия ТЗ: ревьюер проверит её заново…» |
| ТР-56 | Новая версия ТЗ и исправление агентом помечают тесты сценариев этого ТЗ «Устарел» | Тест сценария анализа после новой версии — с отметкой «Устарел» во вкладке «Тесты» и под сценарием |
| ТР-57 | «Сверить с источником» загружает ТЗ из Jira/Confluence заново; если оно изменилось — предлагается новая версия | Изменённая задача → открывается «Новая версия ТЗ» с новым текстом и кнопкой «Проверить новую версию»; не изменилась — сообщение об отсутствии изменений |
| ТР-58 | Исправленный текст обратно в Jira/Confluence не отправляется | После «Исправить ТЗ агентом» задача в трекере не меняется |

### 4.6 Жизненный цикл и модель (шаг 3)

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-60 | Шаг 3 показывает расхождения требований с моделью приложения и разбирается так же, как шаг 2 | Доступны ответ, «Не актуально», массовые действия (только по расхождениям) |
| ТР-61 | Модель приложения учится на ТЗ только когда все замечания исправлены или отмечены «Не актуально» | Пока есть замечание в `open`/`todo`, обучение не запускается |

| ТР-63 | Части модели, которые затрагивает ТЗ, требуют подтверждения | До подтверждения пункт 6 «Пути к тест-дизайну» не отмечен |
| ТР-64 | Сбой сверки ЖЦ можно повторить без потери проверки документа и решений | «Повторить сверку» → новые расхождения; решения шага 2 не изменились |

### 4.8 Одна работа над анализом за раз

| ID | Требование | Критерий приёмки |
|---|---|---|

| ТР-82 | Проектирование сценариев конвейером нельзя остановить из раздела «Требования» | «Остановить» → 409 «Сценарии проектирует запуск конвейера: остановите его во вкладке «Конвейер»» |
| ТР-83 | Работа, прерванная перезапуском студии, через минуту без «пульса» считается прерванной | После перезапуска сервера статус анализа — ошибка/остановлено, действия снова доступны |

## 5. Жизненные циклы

**Анализ:** `running` (идёт работа) → `done` | `error` | `cancelled`. Из `done`/`error`/`cancelled` новая работа
снова переводит в `running`. Удаление доступно в любом статусе, кроме `running`.

**Замечание:** `open` → `todo` (ответ / принято предложение) → `fixed` (ответ внесён в ТЗ агентом или новой
версией); `open`/`todo` → `dismissed` («Не актуально» с причиной). Разобранными считаются только `fixed` и
`dismissed`.

| ID | Требование | Критерий приёмки |
|---|---|---|
| ТР-90 | Переходы, не указанные выше, невозможны | Из `fixed` нельзя перейти в `todo` без новой проверки; `dismissed` можно вернуть в работу только новым решением человека |
