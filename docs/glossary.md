# Словарь терминов студии

Слова, которые встречаются в студии: названия функций, которые в интерфейсе остаются латиницей, и термины
тест-аналитика и инженера, которые студия понимает по-своему. У латинских названий в интерфейсе есть русская
подсказка (наведите курсор). Словарь пополняется вместе со студией: новый термин в интерфейсе — новая строка здесь.

## Функции

| В интерфейсе | По-русски | Что делает |
|---|---|---|
| Studio | Студия записи теста | Экран, где агент проходит сценарий в браузере, а человек подтверждает и правит шаги |
| Auto-Pilot | Автопилот | Агент выполняет шаги сам, без подтверждения каждого; выключен — каждый шаг ждёт «Выполнить шаг» или «Отклонить» |
| Live View | Живой экран | Браузер сессии в реальном времени; у API-теста — запросы и ответы |
| Record & Play | Запись действий | Клик по элементу на живом экране делает с ним то же, что пользователь (кнопка — клик, поле — ввод текста, список — выбор), и становится шагом |
| Element Picker | Выбор элемента | Сначала выбирается действие или проверка, затем клик по элементу на живом экране |
| Planner | Планировщик | Обходит сайт по ссылкам, вкладкам и пунктам меню (только просмотр, без форм и кнопок действий) и строит карту страниц и черновик модели приложения |
| Импорт кейсов | — | Кнопка во вкладке «Тесты»: подтягивает ручные кейсы из Test IT, Allure TestOps или Zephyr Scale, ревьюер разбирает их, агент автоматизирует выбранные |
| Ждёт вас | — | Счётчик решений человека в шапке: ожидания конвейера, замечания ревьюера, обновления модели, самолечение, тесты на ревью |
| Справка | — | Руководство пользователя и этот словарь |
| MCP | Протокол подключений | Способ подключить внешние системы (Jira, Confluence, Test IT, Zephyr Scale, Playwright MCP) и работать со студией из IDE |

## Тесты

| Термин | Простыми словами |
|---|---|
| Сценарий | Что проверить, обычным языком: шаги пользователя и ожидаемый результат. Из сценария агент записывает тест |
| Ручной кейс | Тест-кейс, который тестировщики выполняют руками; лежит в системе управления тестами (Test IT, Allure TestOps, Zephyr Scale) |
| Тест (автотест) | Исполняемый список шагов: действия и проверки с локаторами элементов |
| Шаг | Одно действие (клик, ввод, переход) или одна проверка теста |
| Действие / проверка | Действие что-то делает на странице; проверка (assert) сверяет результат — без неё тест ничего не доказывает |
| Локатор | Способ найти элемент на странице: `data-testid`, `#id`, роль и имя, текст, CSS-путь. У шага их несколько — запасные |
| Плейсхолдер | Подстановка вместо значения: `{{username}}`, `{{password}}` — учётная запись; `{{unique}}`, `{{faker.email}}` — новое значение на каждый прогон |
| Модуль | Повторяющаяся цепочка действий, общая для нескольких тестов (например, вход): правится в одном месте |
| Слой UI / API | UI-тест работает в браузере; API-тест — запросами к серверу приложения, без браузера |
| Черновик / на ревью / в наборе | Статусы теста: записал агент → ждёт проверки человеком → входит в регрессию |
| Тест входа | Тест, который проходит вход («Ещё ▾ → Сделать тестом входа»); с ним Planner входит перед обходом, набор входит один раз, остальные тесты начинают уже вошедшими |
| Повторяющиеся шаги | Раздел «Проект»: одинаковые цепочки действий в стабильных тестах, которые стоит сделать модулем |
| Экспорт | Выгрузка теста в pytest-playwright (`.py`), Gherkin (`.feature`), API-тесты или всего проекта `.zip` |
| API приложения | Раздел «Проект»: адрес API, авторизация API-тестов и каталог эндпоинтов |

## Прогоны и качество

| Термин | Простыми словами |
|---|---|
| Прогон | Один запуск теста в новом браузере: результат, скриншоты, trace, события браузера |
| Trace | Запись прогона Playwright: каждое действие с DOM, сетью и скриншотом — открывается в Trace Viewer |
| Набор | Запуск многих тестов разом (все или по тегам) — регрессия; тесты набора делят данные стенда |
| Расписание | Набор, который запускается сам: в дни недели в заданное время или каждые N часов («Тесты → Запуски наборов → Расписание») |
| Прогон в Studio | Наглядный прогон сохранённого теста: шаги по одному в живом экране, упавший шаг правится на месте |
| Тег | Метка теста (`smoke`, `оплата`), по которой собирается набор |
| Нестабильный тест (flaky) | Упал и прошёл при перезапуске, или часто меняет результат |
| Карантин | Тест, падение которого не валит набор, пока его чинят |
| Устарел | Отметка теста: требования, сценарий или модель приложения изменились после того, как тест записали. Тест прогоняется как прежде; «Тест актуален» или правка шагов снимают отметку |
| Общие данные | Тесты набора работают с одними и теми же объектами стенда — они идут по очереди, а не одновременно |
| Классификация падения | Почему упал тест: дефект продукта, проблема теста, окружение или нестабильность |
| Самолечение | Когда все локаторы шага сломались, ИИ находит элемент заново; новый локатор ждёт решения человека («на ревью») |
| Мутационная проверка | Тест прогоняется на «испорченных» версиях страницы (мутантах) и обязан на каждой упасть |
| Мутант / выживший мутант | Испорченная версия: пропущенный клик, подменённый текст, ошибка сервера. Выживший — тот, на котором тест прошёл: проверки слабые |
| Усилить проверки | Агент воспроизводит тест и добавляет проверки, которые поймают выживших мутантов |

## Требования и ревью

| Термин | Простыми словами |
|---|---|
| Анализ требований | Одна проверка ТЗ со всем, что к ней относится: замечания, решения, сценарии, тесты. Карточка с шагами 1–4 во вкладке «Требования» |
| Ревьюер | Отдельный ИИ на чистом контексте: видит только документ, стандарт и модель приложения — ничего из других сессий |
| Стандарт | По какому стандарту проверяются разделы ТЗ: ГОСТ 34.602, ГОСТ 19.201, ISO/IEC/IEEE 29148, user story |
| Замечание (дефект документа) | Что не так в ТЗ: неполнота, противоречие, неоднозначность, непроверяемое требование |
| Блокирующее замечание | Мешает тест-дизайну; пока не разобрано, сценарии не проектируются. Мелкие (minor, оформление) не блокируют |
| Вопрос авторам | Чего в ТЗ нет и что могут сказать только его авторы |
| Расхождение с жизненным циклом | ТЗ противоречит модели приложения: переходу статусов, правам роли, зависимости |
| Тема | Несколько замечаний об одном, разбираются одним ответом; у тем номера (1, 2… и Ж1, Ж2… у жизненного цикла) |
| Дефект приложения из ответов | Ответ на замечание сообщил, что приложение сейчас работает не так, как должно; в ТЗ записано, как должно быть, а дефект показан отдельным списком на шаге «Требования» — для трекера и тестов |
| Проверить заново (после исправления) | Повторная проверка ТЗ, исправленного агентом: без неё тест-дизайн ждёт, потому что исправления могли противоречить друг другу |
| Покрытие требований | Сколько пронумерованных требований ТЗ проверяет хотя бы один сценарий; требования без сценариев названы номерами |
| Проверяет требования | Поле сценария: номера требований ТЗ, которые он проверяет (M1-REQ-01, ТР-12…) |
| «Не актуально» | Решение человека: замечание не требует правки; причина сохраняется |
| Путь к тест-дизайну | Список под шагами анализа: все действия от проверки ТЗ до генерации тест-кейсов по порядку, сделанные отмечены |
| Источник ТЗ, «Сверить с источником» | Задача Jira, страница Confluence или задача трекера, откуда загружено ТЗ; сверка загружает его заново и, если текст изменился, предлагает новую версию ТЗ |
| Исправить ТЗ агентом | ИИ-редактор правит фрагменты документа по ответам на замечания; прежний текст сохраняется в версиях. Только после него отвеченное замечание считается разобранным |
| Ждёт исправления в ТЗ | Статус замечания с ответом: ответ ещё не внесён в документ, тест-дизайн по нему закрыт |
| Новая версия ТЗ | Исправленный документ целиком от аналитика: заменяет текст и проверяется заново с прежними решениями |
| История изменений | Всплывающее окно с прежними версиями теста или ТЗ: что, когда и кто изменил; у теста — «Сравнить с текущей» и «Откатить» |
| Журнал действий | Кто и когда менял тесты, принимал самолечение, запускал прогоны, менял подключения и права; владелец открывает его кнопкой «Открыть журнал» в «Участниках и доступе» |
| Ревью кейсов | Ревьюер читает ручные кейсы перед автоматизацией: роль и тестовые данные каждого и что помешает агенту (неоднозначный шаг, нет ожидаемого результата, не хватает данных) |
| Уточнение к кейсу | Ответ команды на замечание к ручному кейсу; агент получает его вместе с шагами кейса |
| Общий вопрос | Похожие замечания из разных кейсов, на которые хватает одного ответа («Под каким пользователем входить?»): «Ответить всем» закрывает их во всех кейсах темы |
| Память ответов | Ответы команды на вопросы ревьюеров, сохранённые как факты проекта: тот же вопрос закрывается прежним ответом и больше не задаётся |
| Уверенность ревьюера | Насколько ревьюер уверен, что его предложение совпадает с замыслом авторов, в процентах; по порогу уверенные предложения принимаются сами |
| Решено без вас | Замечание, закрытое прежним ответом команды или уверенным предложением ревьюера; видно в запуске и журнале действий, «Отменить» возвращает его человеку |

## Тест-дизайн

| Термин | Простыми словами |
|---|---|
| Тест-дизайн | Проектирование сценариев по требованиям: что и какими техниками проверять |
| Вид проверки | Позитивная, негативная, граничная, безопасность, доступность и др. — выбирается на запуск |
| Техника тест-дизайна | Классы эквивалентности, граничные значения, таблица решений, переходы состояний, попарное тестирование и др. |
| Gherkin | Запись сценария в виде «Дано / Когда / Тогда» (`.feature`) |
| Переиспользование сценария | Новый сценарий похож на прежний тест: создать новый, переиспользовать или доработать прежний решает человек |

## Модель приложения

| Термин | Простыми словами |
|---|---|
| Модель приложения | Из чего состоит приложение: сущности, их статусы и зависимости, роли и учётные записи, данные стенда — «Проект → Тестовые данные» |
| Знакомство с системой | Первый обход приложения Planner'ом: карта страниц и черновик модели, который потом дополняют требования, кейсы и тесты |
| Сущность | Объект предметной области: заказ, товар, договор, заявка |
| Зависимость | Что должно существовать раньше: заказ требует товар и покупателя |
| Жизненный цикл | Статусы сущности и переходы между ними: каким действием и какая роль переводит (`новый → [оплатить] оплачен (покупатель)`) |
| Роль | Кто работает с приложением: покупатель, менеджер, администратор — с возможностями и ограничениями |
| Учётная запись | Логин и пароль, под которым тест входит в приложение; привязана к ролям. Пароль хранится зашифрованным, ИИ его не видит |
| Данные стенда | Объекты, которые уже есть на тестовом стенде и которые тесты переиспользуют |
| Нужные данные | Данные, которые нужны сценарию, но на стенде ещё не найдены: первый тест найдёт или создаст их |
| Рецепт | Данные, которые тест создаёт заново на каждом прогоне (имя с `{{unique}}`) |
| Память | Факты о приложении, которые агент или человек записал для следующих тестов |
| Часть модели | Группа сущностей или роли: подтверждаются по отдельности, тесту нужны только его части |
| Подтверждение | Человек проверил модель; тесты генерируются только по подтверждённым частям |
| Что изменилось с подтверждения | Изменения части модели после подтверждения: добавленные и удалённые сущности или роли, поменявшиеся статусы, переходы, зависимости; подтверждаются без просмотра всей диаграммы |
| Обновление | Найдено изменение записи, которая уже есть: «было → станет» ждёт решения человека |
| Обновления модели из требований | Обновления, которые предложил текст этого анализа требований; тест-дизайн по нему ждёт, пока их примут или отклонят |
| Дубль | Похожие записи об одном («Заказ» и «Заказы»): объединяются с переносом ссылок |
| Черновик модели неполный | Planner обошёл не всё приложение (лимит страниц или глубины, без входа): того, чего он не видел, в модели нет |
| Другое название (синоним) | Как ещё называют сущность («заявка» для заказа): по нему агент узнаёт сущность в сценарии |
| Проверка перед тестом | Перед тестом сценария: у роли есть учётная запись, сценарий не нарушает ограничений ролей и жизненного цикла |
| Запустить всё равно | Запустить тест, который остановила только проверка жизненного цикла, когда сценарий так и задуман |
| Приложение за входом | Planner нашёл только страницу входа: нужен тест входа, чтобы обойти приложение |

## Процесс и настройки

| Термин | Простыми словами |
|---|---|
| Конвейер | Сквозной процесс: источник (требования, сценарии, ручные кейсы, обход) → сценарии → тесты → прогон → проверка качества → публикация |
| Запуск | Один проход конвейера; его пункты — сценарии или кейсы, у каждого свой статус |
| Продолжить / Перезапустить сбойные | «Продолжить» доделывает остановленный запуск с места остановки; «Перезапустить сбойные» начинает сбойные сценарии с новой сессии |
| Отменить запуск | Прекратить запуск в ожидании решения; спроектированные сценарии остаются в анализе |
| «Нужно подтверждение» | Пункт запуска, на котором агент не справился сам или нашёл возможный дефект: доделайте в Studio |
| «Ждут вашего решения» | Пункты запуска, которые ждут решения человека (замечания к кейсу, подтверждение модели, похожий сценарий), пока остальные в работе |
| Решения команды | Подраздел «Проект → Процесс генерации → Решения команды»: кто что решает, срок решения, ревью по риску, автопринятие предложений ревьюера |
| Мои решения | Раздел «Ждёт вас»: решения, которые настройки проекта отдают вам, со сроками; просроченные выделены |
| Отложить, «Отложенные» | В «Ждёт вас»: пункт уходит из счётчика на сутки (или пока не изменится) и ждёт в свёрнутом блоке «Отложенные»; видно только в вашем браузере |
| Ревью по риску | Политика проекта: тест с сильными проверками (по мутациям), прошедшим прогоном и без самолечения попадает в набор сам; остальные и изменённые агентом — на ревью |
| Без подтверждений | Режим проекта («Решения команды»): автотесты строятся, ничего не ожидая от людей — замечания ревьюера, подтверждение модели, выбор и похожие сценарии не задерживают; решённое без человека пишется в журнал запуска |
| Решений людей на тест | Плитка дашборда: сколько решений приняли люди за период на один новый тест |
| Этап | Шаг процесса со своими настройками: модель ИИ, effort, скиллы, правила; у каждого этапа свой подраздел в «Проект → Процесс генерации» |
| Обзор этапов | Первый экран «Процесса генерации»: этапы конвейера по порядку, включён ли каждый, и переход к его настройкам |
| Скилл | Инструкция для ИИ на этапе (формат SKILL.md): правила команды, примеры, стиль; не может отменить правила безопасности |
| Модель ИИ / effort | Какая нейросеть отвечает и насколько глубоко рассуждает; выбирается в «Проект → Модель», этап может переопределить |
| OpenAI-совместимый API | Общий способ обращаться к нейросети, который понимают vLLM, Ollama, LiteLLM и шлюзы к YandexGPT и GigaChat; по нему студия подключается к модели по адресу из «Проект → Модель» |
| Токены / расход | Объём текста, отправленного ИИ и полученного от него; по ним считается стоимость |
| Лимиты расхода | Предел расхода на сессию, запуск и месяц; работает только для моделей с ценой в «Проект → Модель» |
| Уведомления | Сообщения в Telegram, Mattermost или на почту: итоги наборов, самолечение, лимит, ожидание решений |
| Каталог API | Эндпоинты приложения, собранные из трафика UI-тестов и обхода; по ним пишутся API-тесты |
| Эндпоинт | Адрес API с методом: `GET /api/orders/{id}` |
| Публикация | Отправка теста и результатов прогонов в систему управления тестами |
