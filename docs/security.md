# Для службы безопасности: какие данные куда уходят

Документ описывает студию AI Test Generator в текущей версии. Коротко: в языковую модель уходят
скриншоты и текст страниц тестируемого приложения, но не пароли и не секреты; всё остальное хранится
на сервере студии. В закрытом контуре (docs/offline.md) модель работает на вашем сервере и данные
его не покидают.

## Что получает языковая модель

| Этап | Что отправляется | Чего нет |
|---|---|---|
| Генерация теста (агент) | Сценарий на естественном языке; адрес и заголовок страницы; список видимых элементов (роль, подпись, placeholder, значения полей кроме паролей); видимый текст страницы (до 2 500 символов); скриншот видимой области (JPEG) — на каждом шаге или по запросу агента, в зависимости от настройки «Скриншоты»; логин тестируемого приложения | Пароль: агент видит только `{{password}}`, значение подставляется в браузер в момент шага. Секрет TOTP и одноразовые коды. Cookie и файлы состояния входа |
| Самолечение | Описание шага, старые локаторы, список элементов текущей страницы | Скриншоты, пароли |
| Анализ падения | Шаги теста, ошибка, скриншот после падения, события браузера (ошибки консоли, адреса запросов с кодами 4xx/5xx), история результатов | Тела запросов и ответов |
| Визуальная проверка | Эталонный и текущий снимок, карта различий | — |
| Сценарии из требований | Текст требований (задача Jira, страница Confluence, файл ТЗ) | — |
| Публикация (Zephyr, Allure TestOps) | Название, шаги и результат теста; ответы MCP-сервера системы управления тестированием | Пароли (в шагах только плейсхолдеры) |

Инструменты подключений, которые удаляют данные, моделям не передаются никогда; Jira/Confluence
подключаются только на чтение.

## Что хранится на сервере студии

Все данные лежат в PostgreSQL (docs/deploy.md): пути ниже — ключи строк таблицы `docs`; тесты, задачи,
прогоны и расход модели — в своих таблицах; бинарные файлы — в той же базе или в S3. На диске сервера
только кэш файлов для браузера (`TESTGEN_CACHE_DIR`).

| Что | Где | Защита |
|---|---|---|
| Тесты, история прогонов, скриншоты шагов | таблицы `tests`, `runs`; `data/projects/<id>/` | Доступ к базе и бакету; в студии — роли проекта |
| Playwright trace упавших прогонов | `data/projects/<id>/runs/<тест>/<прогон>/trace.zip` | Пароль заменён на `***`; хранится `run.keep_runs` последних прогонов |
| Трафик (HAR) сценария | `data/projects/<id>/traffic/<тест>.har` | Пароль → `{{password}}`, заголовки авторизации, cookie и поля вида token/secret/api_key → `***` |
| Логины и пароли тестируемого приложения, токены подключений, ключи моделей | `secrets/` | Вне `data/`, не попадают в экспорт; в API только признак «задан»; всегда AES-256-GCM с ключом `TESTGEN_SECRET_KEY` или HashiCorp Vault (см. ниже) |
| Состояние входа (cookie) для прогона набора | `secrets/projects/<id>/state-*.json` | Секрет, как выше; не попадает в экспорт, trace и HAR |
| Ключ подписи сессий студии | секрет `studio/session` | Секрет, как выше; общий для экземпляров студии |
| Пользователи студии | `secrets/users.json` | PBKDF2-хэши паролей (у пользователей каталога пароля нет); API-токены — SHA-256 |
| Журнал действий | таблица `audit_log` | Только дописывание, цепочка хэшей SHA-256, выгрузка в SIEM |

## Сетевые обращения студии

- Языковая модель: адрес API, заданный в проекте («Проект → Модель»; облако провайдера или свой сервер).
- MCP-серверы подключений проекта: Jira/Confluence, Zephyr Scale, Allure TestOps и другие — только если
  подключение создано.
- CDN jsDelivr / cdnjs — один раз за axe-core (проверки доступности); в режиме `TESTGEN_OFFLINE` нет.
- npm — при первом запуске MCP-серверов через `npx`; в режиме `TESTGEN_OFFLINE` нет.
- Тестируемое приложение — браузер студии. Агент не выполняет необратимых действий (оплата, заказы,
  отправка сообщений, удаление): это правило системного промпта, которое скиллы не могут отменить.

## Доступ к проектам

У проекта есть участники с ролями:

| Роль | Может |
|---|---|
| Наблюдатель | Читать всё в проекте, запускать тесты и наборы, выгружать тесты |
| Редактор | Ещё писать тесты (Studio, конвейер, подготовка данных), принимать самолечение, вести задачи, видеть логин тестируемого приложения |
| Владелец | Ещё настройки проекта, учётные данные приложения, подключения, уведомления, скиллы, участники; журнал действий проекта |

- Новый проект видят только его участники; автор — владелец. Проект можно открыть всем пользователям
  студии как редакторам (так работают проекты, созданные до ролей).
- Пользователь без доступа получает 404 на любом ресурсе проекта — тестах, прогонах, trace, файлах
  прогонов, сессиях, задачах, — как будто проекта нет. Проверка одна на все маршруты API
  (`server.guard`), MCP-сервер студии проверяет роли так же; тест обходит все маршруты API.
- Администраторы студии (`TESTGEN_ADMINS` или группы каталога) — владельцы всех проектов; только они
  задают команды и окружение MCP-серверов, настройки моделей и удаляют проекты.

## Вход

- Свои пользователи студии: пароли (PBKDF2), cookie сессии HttpOnly, SameSite=Strict, подпись HMAC.
- **OIDC** (Keycloak, ADFS, Blitz Identity Provider и другие): authorization code + PKCE; у ID-токена
  проверяются подпись (ключи провайдера), издатель, аудитория, срок и nonce. Группы из токена
  (`TESTGEN_OIDC_GROUPS_CLAIM`) дают роли в проектах.
- **LDAP / Active Directory**: служебная учётная запись находит пользователя (фильтр экранируется),
  пароль проверяется привязкой от имени пользователя; пустой пароль отклоняется. Группы — `memberOf`.
- С OIDC или LDAP саморегистрация и локальные пароли выключены (включаются явно:
  `TESTGEN_SIGNUP=on`, `TESTGEN_LOCAL_LOGIN=on` — например, для аварийного администратора). Сессия
  пользователя каталога — 12 часов (`TESTGEN_SSO_SESSION_HOURS`); группы обновляются при каждом входе,
  поэтому исключённый из группы теряет доступ не позже конца сессии.
- Правила «группа → роль в проекте» и группы администраторов задаёт администратор студии
  (Проект → Участники и доступ).

## Секреты

- Каждый секрет в базе шифруется AES-256-GCM (ключ — SHA-256 от `TESTGEN_SECRET_KEY`); путь секрета —
  аутентифицированные данные, поэтому строка одного секрета, подложенная на место другого, не
  расшифруется. Открытые секреты, перенесённые из папок прежних версий (`db import-files`), шифруются
  при переносе; смена ключа — `python -m testgen.vault rotate` (старый ключ в `TESTGEN_SECRET_KEY_OLD`).
- Без ключа студия не запускается. Исключение — база на этом же компьютере (локальная разработка):
  тогда ключ создаётся один раз в `%LOCALAPPDATA%\aitestgen\secret.key` (`~/.cache/aitestgen/secret.key`).
- `TESTGEN_VAULT_ADDR` — секреты в HashiCorp Vault (KV v2, `TESTGEN_VAULT_TOKEN`, `TESTGEN_VAULT_MOUNT`,
  `TESTGEN_VAULT_PREFIX`); в базу они не пишутся.
- Наблюдатели не видят даже логин тестируемого приложения; пароли, токены и секрет TOTP API не
  отдаёт никому — только признак «задан».

## Журнал действий

- Пишется каждое изменение через API: тесты (изменение, удаление, откат версии, подготовка данных,
  учётные данные), самолечение (принято, отклонено, а в режиме «сохранять сразу» — применено без
  ревью, от имени `system`), прогоны и наборы, подключения, участники и права (с тем, чья роль как
  изменилась), настройки моделей и групп, вход (в том числе неудачный), API-токены, экспорт тестов
  и проектов; отказы в доступе тоже. Вызовы MCP-сервера студии и CLI (`testgen.run`, `testgen.auth`)
  записываются с пометкой `via`.
- Запись: время (UTC), пользователь, действие, проект, объект, код ответа, IP, подробности. Тела
  запросов не пишутся — паролей и токенов в журнале нет.
- Каждая запись хранит SHA-256 предыдущей: изменение, вставка или удаление записи ломают цепочку —
  `python -m testgen.audit verify` или «Проверить целостность» в интерфейсе.
- Выгрузка в SIEM: `TESTGEN_AUDIT_SYSLOG=host:port[/tcp]` (syslog, facility auth, запись в JSON) и/или
  `TESTGEN_AUDIT_FILE` (копия в JSON Lines для Filebeat, Fluent Bit); месяц целиком — «Выгрузить месяц»
  или `GET /api/audit/export?month=ГГГГ-ММ`.
- Владелец видит журнал своего проекта, администратор — весь.

## Рекомендации

- Используйте отдельные учётные записи тестируемого приложения с минимальными правами и тестовый стенд.
- Храните копию `TESTGEN_SECRET_KEY` отдельно от резервных копий базы (или используйте HashiCorp Vault).
- Включите вход через корпоративный каталог (OIDC или LDAP) и роли в проектах; выключите
  `TESTGEN_SIGNUP`.
- Отправляйте журнал действий в SIEM и периодически проверяйте цепочку.
- Для систем с персональными данными — модель в закрытом контуре (`TESTGEN_OFFLINE=on`).
